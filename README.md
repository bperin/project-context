# Project Context

[![npm version](https://img.shields.io/npm/v/@bperin/project-context-protocol.svg)](https://www.npmjs.com/package/@bperin/project-context-protocol)
[![CI](https://github.com/bperin/project-context/actions/workflows/release.yml/badge.svg)](https://github.com/bperin/project-context/actions/workflows/release.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](https://opensource.org/licenses/MIT)

Project Context gives coding agents a durable, resumable execution spine for an
existing repository. It keeps one compact plan above narrow implementation
tasks, persists progress outside conversation history, and supports bounded
multi-agent execution without handing product decisions to workers.

## Install

```bash
npm install -g @bperin/project-context-protocol

# or run without installing
npx @bperin/project-context-protocol --help
```

## One workflow skill

Generated workspaces expose one user-facing skill:

```text
/pc-plan start <goal>
/pc-plan continue [PLAN-NNN]
/pc-plan status [PLAN-NNN]
/pc-plan run [PLAN-NNN]
```

- `start` creates a plan only when no non-terminal plan exists.
- `continue` reconstructs state from the plan and task event log, then resumes
  at the first incomplete gate.
- `status` reports persisted state without changing it.
- `run` keeps advancing safe work until it reaches a user gate, planning gap,
  failed hard check, or completion.

Context generation, task registration, readiness, status, graph, inspection,
review, and archive operations remain internal mechanics. They are not separate
slash commands.

## Durable model

```text
PLAN-NNN
└── TASK-NNN
```

There are no epic or separate specification artifacts. `PLAN-NNN.md` combines
intent, repository evidence, decisions, questions, boundaries, acceptance
probes, proof obligations, task strategy, acceptance, and the resume checkpoint.
`TASK-NNN.md` is a narrow execution contract. `data/tasks.jsonl` and the plan
timeline preserve append-only execution history.

Only one plan may be non-terminal at a time. This keeps `continue` and `run`
deterministic and prevents parallel planning trees from competing for context or
repository ownership.

After explicit user acceptance, the persisted plan status is `committed`; the
Planning Gate separately records `User accepted: yes`.

## Planning loop

The root planning agent owns one continuous loop:

```text
repository discovery
  → compact draft
  → self-challenge
  → blocking/advisory user questions
  → revision
  → explicit user acceptance
  → narrow task decomposition
```

Planning uses executable `grilling`; `grill-me` is only its wrapper. `adhd` is
reserved for genuinely open-ended design. Blocking questions stop acceptance
and task creation. Advisory questions remain in the plan with the current
assumption and do not block.

The plan records every completed gate. A later session resumes from disk rather
than replaying the conversation. Material plan changes clear acceptance and
require the user to accept the revised plan.

## Narrow implementation packets

Every task names:

- exact files and symbols it may change;
- API, data, state, and ownership boundaries;
- dependencies and readiness conditions;
- do-not-touch constraints;
- success, failure, and boundary tests;
- verification commands;
- falsifiable proof obligations; and
- conditions that require `needs_planning`.

Implementers do not question the user, choose architecture, or widen scope. If
the plan missed a decision or the required work crosses a packet boundary, the
worker stops and returns `needs_planning` with evidence. The root planning agent
revises the existing plan and affected packets before implementation resumes.

## Bounded multi-agent execution

A plan may use many implementation agents across successive waves. At most
three writers run simultaneously, only when their tasks are dependency-ready and
their exact write sets are disjoint. Unknown or overlapping ownership runs
sequentially.

Each completed packet receives one challenger review. Bounded implementation
defects get one correction pass; planning gaps return to the root agent. Commits,
integrated checks, and manager-state writes remain serial.

## Generated workspace

```text
.<repository>-manager/
├── AGENTS.md
├── .agents/
│   ├── AGENTS.md
│   ├── agents/
│   └── skills/
│       └── pc-plan/SKILL.md
├── workflows/
│   ├── pc-plan.md
│   └── overview.md
├── templates/
│   ├── PLAN-NNN.template.md
│   └── TASK-NNN.template.md
├── plans/
├── tasks/
├── data/
│   └── tasks.jsonl
└── graph/
```

Framework files are regenerated by `upgrade`. Plan and task Markdown are living
artifacts. Task event history is append-only.

## Project-scoped MemoryLake

`init` and `upgrade` add the MemoryLake MCP endpoint to the repository's
`.codex/config.toml` while preserving unrelated Codex settings. Authentication
is kept outside the repository through Codex OAuth; REST automation may use a
`MEMORYLAKE_API_KEY` process environment variable.

Each manager's `data/identity.json` contains a logical MemoryLake workspace and
project binding. A deployment may add the non-secret `workspaceId` and
`projectId`. Planning and resumption then filter every search and write to that
exact project, so repositories can share one MemoryLake workspace without
sharing memories.

The root planning agent owns durable memory writes. It stores concise accepted
decisions, constraints, and verified outcomes. Implementation subagents return
memory candidates instead of writing directly. Credentials, raw reasoning,
transient tool output, and speculation are never stored. The local plan and
append-only task log remain the source of truth for workflow state.
